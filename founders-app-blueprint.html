02System architecture

The app talks to Supabase. Edge Functions are the only code that calls third-party services, so API keys never reach the phone. Webhooks from RevenueCat and Razorpay keep subscription state in Postgres.

03Onboarding & access flow

The path from install to the home feed. A user only gets full access after they are verified and have an active subscription; both are checked by RLS on the server, not just in the app.

Rendering diagram…

04Founder verification flow

This is what makes the network worth paying for. Most registered companies are approved automatically: the company is looked up on MCA and the user's name is matched against its director (DIN) list. Everyone else goes to a manual review queue.

Rendering diagram…

05Subscription & payment flow

There are two ways to pay, and both end in the same subscriptions table. RLS reads that table, so access is controlled on the server. Renewals, cancellations and failed payments arrive as webhooks.

Rendering diagram…

06Connection & chat flow

Connection requests must include a note and are capped each week, so requests stay high-quality. Ignored requests are never shown to the sender as rejected. Chat runs over Supabase Realtime, and push is sent only when the recipient isn't in the app.

Rendering diagram…

07Daily picks matching engine

A scheduled job runs every morning and picks 5 founders for each member using a weighted score. v1 is rule-based; v2 adds pgvector embeddings of bios and "asks".

11Code structure & security rules

The Flutter app is organised by feature, and the server enforces the access rules.

lib/
├─ main.dart
├─ app/
│  ├─ router.dart        # go_router + auth/paywall guards
│  ├─ theme.dart
│  └─ env.dart
├─ core/
│  ├─ supabase_client.dart
│  ├─ revenuecat.dart
│  ├─ push.dart          # FCM token sync
│  └─ widgets/
└─ features/
   ├─ auth/              # phone OTP, social login
   ├─ onboarding/        # profile wizard
   ├─ verification/      # CIN, GSTIN, email, status
   ├─ paywall/
   ├─ home/              # daily picks
   ├─ asks/
   ├─ discover/          # search + filters
   ├─ profile/
   ├─ network/           # connections, requests
   ├─ chat/
   └─ settings/          # subscription, privacy, delete
      ├─ data/           # repositories
      ├─ providers/      # Riverpod
      └─ ui/             # screens + widgets

supabase/
├─ migrations/           # SQL schema + RLS
└─ functions/            # Edge Functions (Deno)
  1. Never trust the client. All access is enforced by Postgres RLS via has_active_access(auth.uid()), not by hiding UI.
  2. Profiles can be read only by members with active access; blocked pairs are excluded both ways.
  3. Messages can be read or written only by the two users in the conversation, and only if they are connected.
  4. Third-party API keys (MCA, Razorpay, MSG91, Gupshup) live only in Edge Function secrets, never in the app.
  5. Webhooks check signatures (Razorpay HMAC, RevenueCat auth header) and can safely run twice for the same event ID.
  6. Rate limits in RPCs: 20 connection requests/week, 5 asks/day, OTP throttling per phone and device.
  7. Admin actions use a separate role, and every action is written to an audit log.
  8. Data residency: Supabase Mumbai region, encrypted at rest, with daily backups (PITR on Pro).
  9. Compliance: DPDP consent at signup, in-app delete/export, Grievance Officer listed in Settings.

12Launch roadmap
